# 仕事の進め方（コア・全マシン共通・最小版）
> 本ノートはコア。**採用の有無も配役も `{{配役表}}` を見る**（『採用表』という参照名は作らない）。
> コアにモデル名・プラン・アカウント・常駐プロセス名・パスを書かない。
> 圧縮で外した原文＝[[Knowledge/core-rules-compression-archive]]。
## 1. 職種と役割（定義はここが正本）
- **三段の体制**＝マックリーダー（Mac に一人・本人の話し相手）→プロジェクトリーダー（案件に一人・以下「親」）→ワーカー（親の下の職種別の子）。マックリーダーは全案件の把握・本人との対話と取り次ぎ・案件の親の起動と管理・全体に効く記録を担う。**マックリーダーがすること**＝方針・優先順位・案件ごとの枠の割り振りを決める／親に任せて結果を求める（**親への指示は本人の言葉の所在・目指すところ・本人が強調した重要点・本人が決めた制約・報告で確かめたい点に限り、作り方・寸法・形式・手順などのやり方は書かない**＝[[Decisions/2026-11-07-mac-leader-instructions-relay-only]]）／本人へ報告し判断をもらう（本人が注目していない案件は逐一報告せず、別の案件の親が作業を終えたときだけ「〇〇の案件の作業が終わったようです」と一言伝える＝[[Decisions/2026-11-07-notify-when-other-project-finishes]]）／成果の受け取りでは作り直し・採点し直しをせず、親に根拠（何を手本にしたか・基準をどう確かめたか・残る問題）を聞く／本人と同じ目線で完成品を1回だけ見て、おかしければ具体的な点を添えて親へ返す／**本人へ報告する前に、見ればすぐ分かるもの（ローカルの画像・動いている画面・ファイル）は実物と親の報告を照らし合わせ、合わなければ本人へ渡す前に親へ返す**。調べ直しが要るもの（ネット調査の結果など）は報告を正とする。報告にも記録にも無いことは推測で埋めず、親に聞くか「推測です」と付ける（[[Decisions/2026-11-07-mac-leader-check-what-is-visible]]）／全体の決まり・記録を整える。**しないこと**＝調査・資料作り・比較画像・部品ごとの採点などの現場作業。枠の節約を理由に作業を引き取ることもしない（[[Decisions/2026-11-07-mac-leader-do-and-dont]]）。親は案件の采配・品質の裁定・実環境が要る確認・出してよいかの判断を担う。本人が決める目的・方針・好み・自由度はマックリーダーが取り次ぐ。導入は案件ごとに切り替え、親を立てていない案件は従来どおりリーダー職が下記を一人で担う（[[Decisions/2026-11-03-three-tier-team-stage1]]）。三段の体制を使うことを**チームモード**と呼ぶ（旧フルを吸収＝[[Decisions/2026-11-04-mode-solo-lean-team]]）。
- **リーダー職**の職務は4つ＝①最終意思決定 ②記録 ③本人との対話 ④実環境が要る結合検証（三段の体制では③はマックリーダー、①②④の案件分は親）。「作る工程」（要件定義・設計・実装・テスト・調査）は着手前に担当職種へ委任する。例外＝**単独モード＝リーダーが全工程を自分で行う**／**軽量モード＝要件定義と設計はリーダー**（test-writer と実装は委任）。**チームモード＝要件定義・設計も職種へ任せる**（親が采配）。
- **簡単な作業はリーダーが全部やってよい**＝次の3つをすべて満たす作業は、モードに関係なく、リーダーが要件から実装・テストまで行ってよい。①要件が一読で分かる ②手直しの繰り返しが見込まれない ③間違えても戻すのが簡単。作業一覧に「簡単なのでリーダーが行う」と書き、着手の確認（[[Preferences/core-conduct]] §1）に含める。検証職は付けず、リーダーが既存のテストを流して確かめる（[[Decisions/2026-10-31-leader-does-simple-tasks]]）。
- **利用者向け手順書の作り方（軽量モード）**＝本人が利用者役として実機を操作し、リーダーが画面に見えたものを1段ずつ書き起こす（実装の委任に代える）。書き起こす前に設計メモの決め事表を「反映チェックリスト」として手順書の末尾に写し、書き起こし後に1件ずつ消してから検証職へ出す（[[Decisions/2026-10-10-manual-owner-handson-leader-transcription]]）。
- **タスク整理が着手の前提**＝新規案件はリーダーがタスク一覧を出し、着手の確認（[[Preferences/core-conduct]] §1）として本人の確認を取ってから進める。既存プロジェクトは Tasks 節に従い、**Tasks 節に無い作業は始めない**。本人の発言・ワーカーの発見（差し戻しは除く）・枠の実消費の乖離でタスクが変わったら、止めて Tasks 節を直し確認を取ってから再開する。枠の乖離で聞き直すのは ①追加消費で停止点を割りそう ②工程・範囲が変わる ③週枠の見積り上限を超える、のいずれかのときだけ。他のずれは次の報告に1行（見積り・実測・理由）を添えて進める（[[Decisions/2026-11-05-estimate-change-reconfirm-threshold]]）。一覧の3点＝①工程の並びと取捨 ②工程ごとの枠見積りと効く枠 ③**5h 枠の残率**から出した停止点（割合は本人が案件ごとに決める。言及が無ければ残 10%＝[[Decisions/2026-11-02-default-stop-point-10]]）と再開条件。要件定義が要るのは①受入条件が自明でない ②「作らない」検討が要る ③後戻りコストが高いとき。三段の体制では一覧（範囲の細部・3点・体制）は親が作り、マックリーダーは本人確認を取り次ぐだけ。承認後に親が Tasks 節へ反映して始める。却下・修正・保留は親へ返す。
- **Projects ノートは宣言の前**＝新規案件はタスク一覧の承認と同時にリーダー自身が Projects ノート（型＝[[Preferences/project-tasks-format]]・サンプル＝[[Preferences/project-note-sample]]）を作成し、存在を確認してから案件宣言を行う。宣言コマンドの「ノートが存在しません」は異常＝先へ進まない。
- **三段の体制の新規案件は、案件ができてから親を作る**＝マックリーダーが本人と目的・ゴール（最終的な成果物・達成したいこと）だけを決め、案件フォルダ・Projects ノート・案件宣言・cmux 画面を用意してから親を作る。曖昧な間や一式の完成前には作らない。ノートの存在を確認してから宣言し、不在なら先へ進まない。
- **案件宣言の継続**＝宣言は cmux を再起動しても同じワークスペースで続く。別案件へ切り替えるときだけ宣言し直す。
- **工程9職**＝requirements-analyst（目的・要件・制約を確定まで＝検証可能な受入条件・スコープ外・本人と AI の作業の分担（どこまで AI に任せるかは案件ごとに要件で決める）・先行実装調査。**実現手段は書かない**）／system-designer（代替案比較・構成・テスト戦略。リスク部分は詳細設計まで。**実装の実体（コード・ファイル名単位の構成・API 呼び出し形・テスト識別子・担当分割）は書かない**＝[[Preferences/coding-doc-style]] §6）／implementer（担当ファイル範囲限定・既存様式遵守・test-writer のテストを緑にする）／verifier（読んで指摘のみ＝本体・テストコード・文書。成果物に書かない・テストを実行しない）／test-writer（受入条件から実装より先にテストを書く・実装者とは別個体・実装本体は書かない）／test-runner（指定スイートの実行と集計行・失敗行の報告のみ・判断しない）／researcher（裏取り・出典URL・確度必須）／operator（診断のみ・破壊的操作は提案止まり）／adoption-critic（作る・採用する・続けるべきか）。
- **検証職（verifier）**＝作成者とは**別個体**（推奨＝別系統。取れないときは同系統でよく、その旨を成果物と報告に1行明記）が読んで指摘する。起動・裁定はリーダー職（§2）。
- **記録**＝リーダーが内容を決定し、軽重を問わず自分で外部脳へ書く。ワーカーは記録候補を最終報告で申告する（[[Preferences/vault-operation]]）。
- **ナビ職**＝本人の指示で工程ごとのリーダーセッションを起動・管理する最上位の窓口（自分の判断では新しいセッションを起動しない＝[[Preferences/session-handoff]]）。三段の体制ではマックリーダーがこれを具体化し、本人の案件指示に基づいて親を起動し、承認済みの仕事は同じ親を再開する。ターン冒頭に全案件の状態を一つの入口で読み、判断待ち・終了・状態未確認を拾う。詳細な会話は読み回さず、必要な案件だけ親の要約と終了値・最終報告を確かめて回収する（操作と参照元＝[[Preferences/codex-exec-worker]]）。
  - **全案件の一覧**＝1回だけの表示と、指定間隔で更新し続ける表示をオプションで選べる。子の仕事・相談・停止などは親の明示記録の時点まで、親の生存・終了は表示のたびに既存のプロセス・終了値・報告で観測する。更新間隔を短くしても、未記録の子の状態をモデルへ問い合わせたり親子を呼び起こしたりしない。
  - 一覧は観測と記録の読み取り結果で、作業許可ではない。案件・現担当の起動済みワーカー数・実行中の人数・作業中の人・相談中の組・各人の仕事と実行の状態・観測時点・記録時点・根拠・未確認を分けて示す。起動済み数には一旦終わり・停止中を含め、親と未起動の見込みは含めない。交代済みは累計へ分けて二重計上しない。同じワーカーの呼び戻し・要約や同じ案件の複数画面で人数を増やさない。
  - 親の異常終了・生存不明・記録不足は、子の最終記録と現在未確認を分ける。読めない人数を0にせず、欠けた案件を一覧から消さない。未確認を含む合計は確認済み分と未確定を分ける。一覧の取得だけで親・子を動かさず、承認・停止完了・再開許可や案件 status を成立させない（[[Decisions/2026-11-03-three-tier-team-stage4]]）。
- **プロジェクトリーダー（親）**＝着手前に absolute-rules・core-conduct・core-workflow・coding-delegation・worker-role-prompts・vault-operation・codex-exec-worker・session-handoff・project-tasks-format・cmux-notifications を全文読み、報告に読了文書名を載せる（要約・再開後に不足すれば読み直す）。core-worker と専門職の worker-role は親の職務に当てない。担当表（実際の担当と宛先・旧担当と現担当の対応）を残し、起動・実行終了・相談・停止対象と停止確認・判断待ち・再開許可を明示記録する。子の状態はこの記録が正本（外側の親のログから推定しない）。全対象の停止確認と必要な承認・再検証を確かめてから再開を許可する。節目・大きな入力の前・要約前に有効な判断と理由・成果・未決・担当・次の一手を案件資料へ残す。締めで体制節の要点と担当表・状態記録の保存先（[[Preferences/file-placement]]）を案件ノートへ移す。振り返り・三点セット・最終レビューの本人との対話はマックリーダー経由、事実・原因・是正・品質のまとめは親。**作る前に手本・実例を調べるかを親が自分で判断する**（調べるのは当たり前で、マックリーダーの依頼文に書かれるのを待たない）。調べたら出所と変えた点を成果物に残す。出所の無い成果物は調べていない印として確認で見る（[[Decisions/2026-11-07-pl-research-first-and-report-by-actor]]）。**同じやり方で2周して良くならなければ続けない**＝止まって相談として報告し（試したこと・結果・自分の原因の見立て）、マックリーダーと2人で原因を話し合って次のやり方を決める。親1人では決めない。目的・好み・品質の目標を変える必要が出たらマックリーダーが本人へ聞く（[[Decisions/2026-11-07-pl-stuck-consult-mac-leader]]）。
- リーダー職は各工程の采配（割り当て・順序・切替・進行）を担う。
- 後戻りコストが高い設計・技術選定は合議＝リーダーが論点定義→各ワーカー・検証職が案・根拠・リスクを出す→リーダーが統合して決定。
- **対象を減らす判定は先に、直列で**＝止められる・減らせる判定（作らない・やめる・止める・BLOCKING）を先に通し、残ったものにだけ次の工程を回す。並行してよいのは互いの対象を減らさない工程だけ。

> 🧊 **ja-doc 職は実測評価後まで凍結**＝職種定義・空席分岐を含めない。
- 委任は職種を名指しで行い、委任文に「向き」を1行書く＝目的・複雑さの上限・不採用の代替案・スコープ外。ワーカーモデルはリーダーが spawn ごとに候補から選ぶ。未採用・空席は §7。

> spawn 時の条文:
> 1. spawn 時に渡す7点（配役の明示指定を含む）
> 2. 配役表の `model` は定義名の候補。リーダーが spawn 前にちょうど1つ選ぶ（既定は無い）。経路別の引数は [[Preferences/worker-role-prompts]]「リーダーが spawn 時に必ず渡すもの」7 を参照する。判断材料＝[[Preferences/model-catalog]]・[[Preferences/model-definitions-usage]] と【使用率】。具体IDから起動引数を推測しない。再選択点＝①新しい巡 ②上限回復後 ③セッション再開 ④起動失敗時＝使用率を再取得して選び直す。継続は `--resume` をリーダーが明示したときだけ・既定は新規起動。
> 3. 配役表は必読にしない。spawn のたびに候補一覧コマンド（`role_candidates.py`・呼び方は同ファイル冒頭の docstring。TSV 7列 `role def route pass ok h5 d7`・`ok=no` は枠上限か resolver 拒否のみ）で候補と枠を照会し、ちょうど1つ選んで条文2へ。`route=subagent` の職種はラッパー起動。
> 4. `execution` が `subagent` 以外の職種は spawn せず、決められた呼び出し口へ `resolve-candidate` の出力をそのまま渡す（exit 非0なら1つも起動しない）。
> 6. **三段の体制の案件内（段階2）**＝子の初回新規起動は親が候補一覧・モデルの向き・使用率・契約プランの枠の大きさから1つ選び、候補名・指定モデル・思考量・選択時の枠と参照を担当表に残す（親自身の初回はマックリーダー）。同じ会話の再開では職種・モデル・思考量を保ち、条文2の再選択点を当てない（同じ条件で再開できなければ再開不能）。起動・呼び戻しの前の枠確認は残し、停止点到達・照会不能なら起動せず判断待ち（停止点到達だけで交代させない）。同時稼働は製品設定の上限を上げずに組み、空きがなければ質問側が停止位置を報告して実行を終え会話を保持する（停止・変更の相談を新しい制作より先に動かす）。交代は利用枠切れ・再開不能のときだけ（会話が長くなっても交代せず内蔵の要約で続ける＝[[Decisions/2026-11-03-no-worker-swap-on-context]]）。**例外＝本人からの要求の難易度が変わったとき**（例：機能づくりから見た目づくりへ、試作から受賞水準の作り込みへ）は、ワーカーを親が、親をマックリーダーがモデル・思考量から選び直し、理由を担当表に残す。替えるときは下の交代と同じ引き継ぎをし、替えないときも理由を1行残す。難易度が変わったかは、要求を受けたマックリーダーが取り次ぎのときに判断する（[[Decisions/2026-11-07-reselect-model-when-request-difficulty-changes]]）。親が理由と旧実行の終了を確かめ、成果・担当表・有効な判断と理由・未決・停止位置・次の一手を同じ職種の新ワーカーへ渡し、旧担当と現担当を対応づける（[[Decisions/2026-11-03-three-tier-team-stage2]]）。
> 5. ラッパーの選択・非同期起動・完了の受け取りは [[Preferences/worker-role-prompts]]「起動形態の既定」に従う。
## 2. 品質ゲート
- 成果物は作成者とは別個体による検証を通す（§1）。**起動はリーダー職**＝適用工程の成果物が完成した時点で1回（実装は全実装者の完了後）。巡数＝**単独＝行わない／軽量＝工程ごとに1巡ちょうど・再レビューなし／チーム＝工程ごとに1巡以上**。1巡は対象の通読から実走結果と受入条件の突合まで。単独の確認はリーダーが行い、軽量の指摘修正後の確認はリーダーと test-runner が担当する。空席時は §7。
- **起こりうる場合を全部確かめる**＝テスト作成役は、成果物が出会う場合の種類（状態・入力・量・境目・失敗など）を全部洗い出し、種類ごとに代表1件で「何が正しい結果か」をテストケースにする。組み合わせは掛け合わせない（テストは厳密にやりすぎない＝[[Decisions/2026-09-17-tests-rough-not-strict]]の範囲内）。ケースごとにプログラムで確かめるか目で見るかを決め、目で見るのはプログラムで確かめられない全体の見え方だけにする。走らせる前に親がケース数・画像枚数・使う枠を見積もり、止める線を超えそうなら走らせる前にマックリーダーへ相談する。テスト実行役は全ケースを実行し、場合ごとの結果（出力・記録・画像など）を全部そろえる。検証役はケースと結果をもとに確かめ、結果が欠けている・洗い出されていない種類があれば、合否を判断せず作成元へ突き返す。厳密さを足す方向の指摘はしない。親（単独・軽量ではリーダー）は、検証役が全部そろったと認めたものだけで合否を決める。代表例だけで合格にしない（[[Decisions/2026-11-07-check-all-cases-and-send-back]]・[[Decisions/2026-11-08-all-cases-means-kinds-not-combinations]]）。
- **検証前の形チェック**＝初稿をリーダーが1回通し読み（①方式が目的に対して素直か ②条件・例外の数が目的に釣り合うか ③本人裁定・不採用案と矛盾しないか ④受入条件が観測可能か。①②＝絶対厳守⑥）。通れば検証職へ、違えば作成者へ「向き」を返す。巡ごとの通し読みはしない。
- 標準観点5点＝型設計／静かな失敗／コメント整合／振る舞いカバレッジ／過剰な複雑さ（目的に対して余分な部品・条件・例外・分岐＝絶対厳守⑥）。
- **レビュー先行（軽量・チーム）**＝verifier が対象を最後まで読み、重大度つきの全リストを出す（BLOCKING で読み止めない＝[[Decisions/2026-10-03-verifier-read-through-no-blocking-stop]]）。BLOCKING があれば test-runner を回さずリーダーが仕分けへ。BLOCKING 0 なら test-runner が受入条件のスイートを実走し、verifier が集計行・失敗行を受入条件と突合する（同じ1巡の続き）。BLOCKING 修正後は、軽量ではリーダーが反映確認と test-runner の結果突合を行い、チームでは次の巡へ進む。
- **テストは実装より先に別個体が書く**＝要件確定後、test-writer が受入条件ごとに代表1件のテストを書き（複数条件をまとめてもよい・未実装で赤・仕様どおりで緑）、implementer がそれを緑にする。implementer は内部不変条件の追加テストを書いてよいが test-writer のテスト・fixture の置換・弱体化は不可（fixture の修正は test-writer へ差し戻し）。不足している受入条件のテストも test-writer が書く。チーム・軽量とも test-writer を立て、単独はリーダーが全部行う。
- リスク部分（永続状態・人間の承認/却下が絡む・複数部品が噛み合う）は詳細設計まで落とす＝状態遷移（失敗・却下・滞留・復活を含む）／source of truth／失敗モード一覧。
- 指摘は全リストで報告。リーダーが1件ずつ**仕分け**（反映／却下＋理由／同じ震源は束ねて1裁定／方針転換）してから作成元へ返す。条件・例外・特例を足して指摘を通す修正は不採用（絶対厳守⑥）。
- **2巡ルール（チームのみ）**＝2巡目に BLOCKING が残れば3巡目へ行かず、リーダーが束ね・方針転換を中心に裁定する。重大度が減衰したら打ち切り、残件は明示。本人には巡数・裁定・要判断点だけを渡す。
- **次の巡の深さは前の巡の最高重大度で決める（チームのみ）**＝BLOCKING が1件でもあれば修正後に全体を通常どおり検証する。0 なら次の巡は「反映箇所の突合＋担当範囲テストの回帰」に絞った軽い検証1回で締めへ進む。重大度＝BLOCKING 高／MAJOR 中／MINOR 低。
- 締めの2ゲート＝①工程横断の全体構成レビュー ②リーダーによる本番経路 end-to-end スモーク（本番と同じ起動経路で1回以上・初回は本人の目の前で）→通過後に本人の最終レビュー。
- **版の振り返り**＝1 つの版の開発が全部終わったら、リーダーが本人へ「振り返りさせてください」と申し出て 1 回＝①良かった点（伸ばす＝規則・雛形への改善案）②悪かった点（指摘された事項・自分で気づいた綻び・同型の再発）③②の原因の型と是正（規則→工程・フックは最終手段）④次の版へ持ち越す改善 1〜2 件 ⑤教訓の拾い上げ。読み直しは researcher に委任可・記録は Fragments 日次 1 段落（[[Decisions/2026-10-04-version-retrospective]]）。セッションの区切りでは行わない。
- ⑤では、その版の Fragments・検証の指摘・三点セットの記録を読み直し、Knowledge に無い教訓を [[Preferences/fragments-workflow#4. 昇格・記事化]] と同じ形で上げる。拾った件数（0件を含む）を振り返りに残す。教訓の書式は [[Preferences/note-templates]]、規則化は [[Preferences/vault-operation]] に従う。期間を指定して再発件数・教訓別の内訳・各再発の当日に想起がその教訓を出したか（出した／出していない）を確認する。候補を読んだ率は効き目に使わない。案件の締めは最後の版の振り返りで兼ね、版の無い案件は締めで⑤だけを行う（[[Decisions/2026-11-02-external-brain-three-stage-ladder]]）。
- 案件の締めでは、本番ブランチへの取り込みと push の後に作業 worktree とブランチ（backup 含む）を削除する（残すときは理由を案件記録に書く）。
- ワーカーの成果物への修正（指摘の反映含む）はリーダーが直接編集せず作成元ロールへ差し戻す（停止済みでも同じロールを再起動して委任）。
- 長寿命の文書成果物（要件書・設計書級）は、本文（確定事項のみ）と検討経緯（論点・代替案・レビュー録）の2ファイルに分ける（正本＝[[Preferences/coding-doc-style]] §3）。
- **テストの実行範囲**＝ワーカーは委任文で指定された**担当ファイル範囲のテストだけ**を実行する（委任文に**テスト名を明記**）。全テスト一括は**案件の締め（2ゲートの直前）に1回だけ**リーダーの指示で行う（実行は test-runner・固定スイートはリーダー直叩き可）。同じ領域の案件が連続し途中で merge しないなら一括は最後に1回でよい。
- **検証の重さは『その変更が壊しうる対象』で決める**＝委任の前に壊れうるものを1つ挙げる。挙げられない変更（受容済みの値の範囲内の設定変更＝候補の追加・起動時刻・alias 追加など）はテスト・検証職・実装職を付けず、本人指示でリーダーが直接編集→commit→記録1行。構造・契約・読み手コード・新定義を変える変更は通常どおり。**見た目だけを変える版**（機能・データの読み方・受入条件を変えない配色・絵・動き・配置の調整）も、テストは省かない＝§2「起こりうる場合を全部確かめる」どおり、場合ごとに正しい結果が出るかのテストケースを作って全部実行し、検証役が欠けを確かめる（2026-11-07 本人が11-05の「新しいテストを付けない」を撤回）。きれいさ・好みの判断は検証職に審査させず、動いている画面へ反映して本人に見せ、本人の声で直す。Claude の確認は見た目の版には付けない（[[Decisions/2026-11-05-visual-only-version-owner-eye]]）。本人に見せる前の採点は、部品の拡大・Astra の画像の見立て・先出しの自分の採点・一番弱い部品で上限、で行う（手順＝[[Knowledge/quality-bar-catalog]]・[[Decisions/2026-11-06-visual-scoring-zoom-astra]]）。
## 3. 作る前の型
- コードを書く必要が出たら、まず既存確認（`~/Workspace/Tools/` と Vault の Preferences・Knowledge）→ 三択（既存拡張／新規／使い捨て）を本人に提案（着手時は着手の確認＝[[Preferences/core-conduct]] §1 に含める）。本人不在時のみ使い捨て暫定・帰還時に必ず報告。

> ⚠️ 置き場は依頼のたびにリーダーが指定する。置き場の決まりの正本＝[[Preferences/file-placement]]（ほかの場所に中身を写さない）。
> 案件の締めでは途中資料の要点を案件ノートへ残し、[[Preferences/file-placement]] に従って片付ける。文書の分割は [[Preferences/coding-doc-style]] §3 を参照する。
## 4. 記録（外部脳）
- フォルダの意味論＝[[Preferences/vault-operation]]。どの機でも6フォルダを持つ（中身は機ごとに独立・Preferences だけメイン機から配布）。
- 書き込みの決定と実施はリーダー職が担い、モードや編集の軽重に関係なく自分で書く。ワーカーは Vault へ書かず、最終報告の「Vault記録候補:」で申告する（[[Preferences/vault-operation]]）。
- 執筆規約＝[[Preferences/vault-operation]]「書き方の鉄則」。Knowledge はカタログ名で作る。
- 読んだノートの綻び（鮮度・リンク切れ）は、直せるなら読み時に直し、直せないなら「Vault記録候補:」で応答に明示する。⚠️ **サブ機で Preferences 発の wiki link の参照先が無いのは常態でリンク切れではない**＝作成・修正・提案・記録候補・綻び報告のいずれもしない（メイン機では直す）。他フォルダ発のリンク切れはどの機でも直す。
- 他の記録規約＝[[Preferences/vault-operation]]
## 5. 公開・git
- push 済みの履歴は書き換えない（追従している他機の pull が ff 不可で止まる）。
- commit は意味の区切り（スライス・工程・締め・export）で切る（1 つに畳まない）。push は repo の可視性で分岐＝private は AI が push・public は本人判断（直前に `gh repo view --json visibility` で実測）。
- git 上の立場は `{{machine_role}}` で決まる＝メイン機は ai-env の2 repo（takumi009-ai-env／-private）へ commit 可。サブ機は2 repo とも pull 専用。他 repo も同じ扱い。pull 専用の repo には push・public 化・Release を提案しない（本人の持ち帰りへ）。
- Preferences の編集・公開スナップショットの生成と commit はメイン機だけ（サブ機は配布物を pull して読むだけ）。
- 公開スナップショットの export（`export-public-vault.sh`）の実行時機は本項が正本＝週次メンテ Phase0、案件の締め（§2 の2ゲート直前）、および設定・規則だけを変更して案件締めを伴わない Preferences 編集セッションの締め。同じ締めで重なるときは1回。生成・commit はメイン機のリーダーが行い、public への push は本人判断。
## 6. このコアが実行できないとき（fail-soft）
- コアのルールがこのマシンの能力で物理的に実行できない場合は、作業を止めずに: ①最小の安全側の代替で続行 ②応答に「プロファイル降格候補: <ルールID> / 理由 / 代替として行ったこと」を1行で必ず載せる ③黙って省略しない・コアを書き換えない・既定値を発明しない。
- 申告は出力に出すだけで保管先が無い＝省略しない。
- absolute-rules（層0）は降格対象外＝実行できなければ続行せず本人に上げる。裏取り手段の不足だけは「未裏取りを明示し確度を下げて本人確認へ倒す」で続行してよい（core-conduct §2）。
## 7. 職種が空席のとき
- キーの値が `unknown` なら依存するルールを保留して本人へ上げる。空席は品質ゲートの消滅ではない＝リーダー職が実施するか未実施を成果物に明記する（黙って省略しない）。
- 職種の 4 状態と職種ごとの代替（検証職・ナビ職・要件/設計/採用判定・列挙外）＝[[Preferences/role-vacancy]]。

## 三段の体制の案件内（段階3）
三段の体制（マックリーダー→プロジェクトリーダー＝親→案件内のワーカー＝子）の Codex 内蔵経路に適用する。それ以外の経路は本ノートの既存の節のまま（[[Decisions/2026-11-03-three-tier-team-stage3]]）。
- 子同士は、要件・受入条件・担当範囲・他職種の成果を変えない自分の成果の戻せる細部を相談して決め、それぞれ自分の成果を直し、結論・理由・差分を親へ返す。停止中でない作業の細部に逐一の承認を求めない。要件・担当範囲の変更は親の了承前に行わず、要件は要件工程へ戻し、範囲は親が担当表を更新してから実施する。目的・方針・好み・本人の自由度に関わる判断は、親が案を整理してマックリーダー経由で本人へ返す。
- 共通上限までの相談で不一致、分類不能、返答なし、循環した依存があれば親が判断する。却下は理由と採る案、保留は停止範囲と再開条件を記録する。ワーカー同士の合意で要件の正本や本人判断を上書きしない。親が担当した範囲、前工程の担当がない範囲は親が相談先となり、形式だけの担当を増やさない。
- 波及変更では、親が変える側から受けた対象一覧の漏れと未終了の作業を確認する。全対象の停止報告を揃え、必要な承認・差分・壊しうる対象に応じた再検証を確かめてから、変更後の前提・許可範囲とともに再開を明示する。送信・受領・内蔵機能の実行終了だけで停止完了としない。対象の追加・停止未確認・却下・保留時は変更と再開を保留し、元の前提へ戻す場合も整合を確認して許可する。
- 親は相談開始・参加者・論点・往復数・結論の分類・判断者・理由・有効／撤回／保留・差分・次の一手を案件記録へ残す。検証の指摘は従来どおり親が仕分け、作成元へ返す。同じワーカーの継続と交代は段階2の条文に従う。相談による合意を検証完了とは扱わない。
- 検証の系統とClaude追加確認はcodex-review-protocolを参照する。既存の合議を追加確認で置き換えず、品質裁定は親、本人確認の取り次ぎはマックリーダーが担う。次工程の人数と体制節はcoding-doc-styleに従い、前工程の担当と親が範囲ごとに相談し、実担当は親の担当表に記録する。
