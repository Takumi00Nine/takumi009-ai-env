# ノート本文の軽い型カタログ（推奨・強制しない）

AI がノートを書くときの推奨スケルトン集。**テンプレ穴埋めを義務にしない**（即時 capture の速度が最優先）。型に合わない知識は自由形式でよい。共通原則＝結論を冒頭に／1ノート約8,000字以内／aliases は「ユーザーが打ちそうな語」／メタデータ（frontmatter）は既存規約どおり。

**Knowledge のノート名・単位は「後で追記・統合される前提」で付ける（2026-07-21 本人指示）**: 個別事例名で切らず、将来の同類が collect できるカタログ名にする（実例: `bgmer-free-bgm`（個別サイト名）→ `free-bgm-sites`（フリーBGMサイト一覧）に改名。BGMer はその1エントリ）。本文もカタログ構造（サイト/項目ごとの節＋「新しく使ったら追記する」運用文）にしておく。
**Why:** 個別名のノートは同類が増えるたびに分裂し、knowledge-merge の統合コストになる。最初から器を大きく作れば追記だけで済む。
**How to apply:** Knowledge 新設時に「これの同類は今後増えるか?」を自問→増えるなら一覧/カタログ名＋カタログ構造で作る。単発性が確実なもの（特定バグの罠集等）は従来どおり個別名でよい。

## 型1: 罠集（技術的な落とし穴の記録）

```
# <対象> の罠集
## 罠N: <一言で現象>
- 現象 → 確定条件（実測でどう再現するか） → 対策 → （あれば）出典
```
実例: 実測値・境界条件・「見かけの症状と真因の違い」を必ず残す。

## 型2: 判断記録（Decisions/）

```
# <何を決めたか>
**決定（YYYY-MM-DD・決定者）:** 一文で。
## 経緯 / ## 選択肢と判定（A vs B＋根拠） / ## 適用（波及チェック: grep語と修正ファイル）
```

## 型3: 手順書（繰り返し実行するオペレーション）

```
# <手順名>（正本）
## 前提チェックリスト（スキップ禁止事項） / ## 手順A: 通常系（番号付き） / ## 手順B: 異常時 / ## 制約（変更しないこと）
```

## 型4: 台帳（所有物・契約などの事実一覧）

```
## <カテゴリ>（確認日）
- **品名/契約名**（型番・ASIN・月額など機械照合できる識別子・一言の用途）
```
1項目1行・確認日を残す・変更があれば行を書き換え（履歴は git）。

## 型5: 調査結果（Web・実測のリサーチ）

```
# <問い>
結論（1〜3行・確度と調査日） → 根拠（実測値・比較表） → 出典（一次情報URL） → （必要なら）review_by
```

> 迷ったら型を探すより先に書く。型はあとから整えられるが、書き漏らした事実は戻らない。
