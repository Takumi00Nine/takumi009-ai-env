# 設計・記述の運用ルール（共有ライブラリ分離／資料の新旧同期）

夜間バッチの昇格提案 frag-2c396e816aea を本人承認で昇格（2026-07-20。初出＝Fragments 2026-07-16 の本人指摘2件）。

## 1. 共有ライブラリは実行エントリポイントに同居させない
複数の呼び出し元から使われるコードは、CLI スクリプト等の実行エントリポイントに同居させず、独立ファイルに分離して「共有資材として参照される」構造にする。

**Why:** CLI と lib が同居すると責務が曖昧になり保守性が下がる（実例＝vault_inventory の CLI/lib 同居指摘。一般則化＝[[Decisions/2026-07-16-simplification-item-cleanups]] 項目10）。

**How to apply:** 新規実装・委任時の設計段階でエントリポイントと共有部を分ける。レビューで同居を見つけたら分離を指摘する。

## 2. 資料の改訂は「本文＋差分」をセットで更新する
設計書・要件書など、本文と差分（変更点まとめ）の両方を持つ資料を改訂するときは、必ず両方を同期して更新する。

**Why:** 片方だけ更新すると新旧の記述が食い違ったまま残り、後から参照した側が誤った情報を掴む（実例＝設計書 v1/v2 の不整合指摘）。

**How to apply:** 改訂タスクの完了条件に「本文と差分の両方を更新した」を含める。ワーカー委任時はプロンプトに明記する。

## 3. 現行本文と経緯アーカイブを別ドキュメントに分ける
長寿命ドキュメントは現行本文（結論・現行設計・受入条件）だけを正本とし、経緯（改訂履歴詳細・却下案・レビュー指摘表・論点台帳）は別のアーカイブ文書へ分離して相互リンクする。改訂時も経緯は本文へ追記せずアーカイブ側へ書く。

**Why:** 正本が経緯で肥大すると参照・整合コストが増え、文書間整合バグの温床になる（実例＝共通コア分離設計書。詳細＝[[Decisions/2026-08-30-doc-body-archive-split]]）。

**How to apply:** 新規の設計書・要件書は「本文＋アーカイブ」の2ファイル構成を既定にし、ワーカー委任プロンプトへ明記する。レビューで混在を見つけたら分離を指摘する。実装完了した設計書は正本を実装側（コード・運用ノート・Decision）へ世代交代させ、歴史文書化バナーを付ける。撤回・廃止・却下した条文と旧案は、打ち消し線や「廃止」注記の形でも本文に残さず経緯側へ移す。本文には欠番の案内1行だけを置く（実例＝2026-09-06 3モード設計書・要件書 v1.24 の ~~FR-6~~ 等）。

- 適用範囲＝工程7職種すべてのファイル成果物（要件書・設計書・実装の変更記録・テスト結果・調査報告・巡回／障害報告・判定書）。本人指示 2026-09-06＝要件書・設計書級に限定しない。後から参照するのは本文だけで済むようにする（正本の適用先＝[[Preferences/core-worker]] §3）。

## 4. 受入条件・判定規則の書き方（2026-09-05 追加）
- 受入条件に fixture の**総数と内訳**を宣言させる。宣言した数と列挙が食い違えば、誰にも検査されていない条件を数で検出できる（実例: 「7分類」と書いて5分類しか並んでいなかった AC が数の突合で判明）。
- 既存の判定規則を持つ場所へ規則を1つ足すときは、**既存規則の中での評価順（先勝ち・後勝ち・例外）まで書き下ろす**。順序を書かないと、正しい実装のほうが受入条件に落ちる矛盾が生じる（実例: 「429 の後は分類を維持」が先勝ち評価順と衝突）。
- 本人が値を決めていない設定に、機構が既定値を発明しない。**未設定は「線が無い」であって「0」ではない**。他所の実装の既定値を自分の既定の根拠にしない。代償は正直に書く＝本人が線を1本も引かなければ予防は「残量0のとき」まで縮む、それでも「根拠の無い線で止められるより、線が無いことが見えているほうがよい」（提示に設定の有無を出す）。閾値・重み・係数を根拠なく置くと、レビューを何巡重ねても収束しない（実例: 数値化案が8巡75件のレビューを経ても解消しなかった）。
- 壊れたデータを見分ける受入条件は、読み手側でなく**書き手側の契約**で書く。受入条件を書く前に「その判定に必要な情報が、判定する側の入力に存在するか」を確かめる。存在しないなら、それは読み手の条件ではなく書き手の条件（実例: 取得に失敗したのに更新時刻だけ更新したキャッシュは、読み手からは正常データにしか見えず識別しようがない。防ぐのは書き手側の契約であり、確かめるのは「書き手に失敗を注入して書かせたデータを読み手に読ませる統合検査」）。
- 受入条件の fixture は陽性・陰性とも必ず ID を振る（陽性を ID 無しで呼ぶと総数宣言が空文になる）。
- 新しい条文を足したら、その文書の「撤回済み・不採用」一覧と突合する（撤回した方式は別の場面の条文で再発する＝2026-09-05 に2度再発）。
- 新しい条文を足したら、その条文が触れるすべての受入条件・fixture・固定文面を**同じ巡で**洗う。伝播漏れは次巡に BLOCKING として返る（2026-09-05 実例＝3モード要件 10〜13巡の BLOCKING 19件中14件がこの型）。
- 記録の型は「案件に1つ」でよい軸と「工程ごと」に要る軸を、**判定式が何に依存するか**で決める。全部を工程別にするのも全部を案件レベルにするのも誤り（実例＝打ち切り理由はモード依存なのでモードは工程別に必要／真理値表の合否は配役に依存しないので検証職は案件レベルで足りる＝2026-09-06 3モード要件）。
- 同じ状況を2通りに書ける表記を残さない（実例＝工程別の空席を足したとき案件レベルの空席形を残すと、1工程の案件が2通りに書けた＝2026-09-06）。
- 大きな撤回の自己スイープは、撤回した ID を引用している箇所だけでなく、撤回した概念を**言葉で言い換えている**箇所まで洗う（実例＝「記録は工程別の内訳を持つ」の一文を見落とし、次巡に BLOCKING で返った＝2026-09-06）。
- 義務を1本の記録先へ集約する変更は、その義務を果たせない既存経路が無いかを必ず確かめる（実例＝単独モードはリーダーが Vault へ書けないため、外部脳への記録義務を無条件にすると達成不能だった。代替経路を「義務を果たしたものとする」形で明記して解消＝2026-09-06）。
- 条文を畳むときは、畳んだ先の文がそれまで別々の条文が担っていた境界を全部含むか確かめる。「短くする」は「境界を消す」と同義になりやすい（実例＝簡素化直後の BLOCKING 4件中3件が、記録職との境界・次巡義務の陽性経路・レビュー対象／対象外の境界が消えた型＝2026-09-06）。
- 受入条件を「〜している工程では」のような条件つきで書くと、前件が偽になる実装が素通りする（空虚な真）。陽性の事例を1件以上要求する形にする（実例＝フルモードが常に1巡で止めれば AC を通過できた＝2026-09-06）。
- 撤回の自己スイープは、本文の条文だけでなく「新旧対照表」「本文から移した根拠」のような**過去を説明する節**も対象にする。これらの節は「現行の結論」を名乗る欄を持つので、撤回が伝播しないと最も誤誘導しやすい（実例＝フックを変えない方針になった後も、判定順の結論が現行として残っていた＝2026-09-06）。
- 要件書・設計書の影響範囲一覧に書く該当箇所の件数（改名対象の行数など）は、記憶や前版の数字を引き写さず、確定直前に grep で実数を取り直して書く（実例＝3モード要件 §8/§10 の件数が再実査で3箇所ずれていた＝2026-09-06）。
- 波及一覧（改訂対象ファイルの一覧）は、同日に新設されたファイルを漏らしやすい。確定直前に対象語で repo と Vault を全文 grep して一覧を裏取りする（実例＝当日新設の core-worker.md と test-update-sub.sh の2箇所が §10 に無かった＝2026-09-06）。
- 同じ終了コード（非0）に新しい意味を足すときは、出力側に読み分けの手がかり（固定文の先頭行など）を同時に足す。足さないと「予定された失敗」と「本当の失敗」が区別できない（実例＝2026-09-06 前提修正設計 P-2＝職種定義の初回未配置と dangling を `AGENTS:` 固定文2本で区別。3モード設計6巡目にも同型の指摘）。
- 新しい契約・前提・受入条件を足したら、同じ巡で①その材料（ログ・ファイル・パス）が現物に実在するか ②収容先（テストスイート・担当）があるか ③既存の全経路と両立するか、の3点を確かめる。足すだけで確かめないと次巡に同型の BLOCKING が返る（実例＝2026-09-06 3モード設計の exec 前提改訂で3巡連続）。
- 「印が無いこと」を別の原因の根拠に使う前に、その経路が本当に何通りあるかを現物で数える。不在からの推定は経路が2つのときしか成立しない（実例＝update-sub の非0原因を2通りと思い込み、現物は4通り以上あった＝2026-09-06）。
