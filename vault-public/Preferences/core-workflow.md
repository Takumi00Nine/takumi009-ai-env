# 仕事の進め方（コア・全マシン共通・最小版）
> 本ノートはコア。**採用の有無も配役も `{{配役表}}` を見る**（『採用表』という参照名は作らない）。
> コアにモデル名・プラン・アカウント・常駐プロセス名・パスを書かない。
> 圧縮で外した原文＝[[Knowledge/core-rules-compression-archive]]。
## 1. 職種と役割（定義はここが正本）
- **リーダー職**の職務は4つ＝①最終意思決定 ②記録 ③本人との対話 ④実環境が要る結合検証。「作る工程」（要件定義・設計・実装・テスト・調査）は着手前に担当職種へ委任する。例外＝**単独モード＝リーダーが全工程を自分で行う**／**軽量モード＝要件定義と設計はリーダー**（test-writer と実装は委任）。
- **タスク整理が着手の前提**＝新規案件はリーダーがタスク一覧を出し、本人の確認を取ってから進める。既存プロジェクトは Tasks 節に従い、**Tasks 節に無い作業は始めない**。本人の発言・ワーカーの発見（差し戻しは除く）・枠の実消費の乖離でタスクが変わったら、止めて Tasks 節を直し確認を取ってから再開する。一覧の3点＝①工程の並びと取捨 ②工程ごとの枠見積りと効く枠 ③**5h 枠の残率**から出した停止点（割合は本人が案件ごとに決める。言及が無ければリーダーが core-conduct §4 の注意の指値・過去実績から案を出す）と再開条件。要件定義が要るのは①受入条件が自明でない ②「作らない」検討が要る ③後戻りコストが高いとき。
- **Projects ノートは宣言の前**＝新規案件はタスク一覧の承認と同時に記録職へ Projects ノート（前提・要件・Tasks 節）の作成を依頼し、作成を確認してから案件宣言を行う。宣言コマンドの「ノートが存在しません」は異常＝先へ進まない。
- **工程9職**＝requirements-analyst（目的・要件・制約を確定まで＝検証可能な受入条件・スコープ外・先行実装調査。**実現手段は書かない**）／system-designer（代替案比較・構成・テスト戦略。リスク部分は詳細設計まで。**実装の実体（コード・ファイル名単位の構成・API 呼び出し形・テスト識別子・担当分割）は書かない**＝[[Preferences/coding-doc-style]] §6）／implementer（担当ファイル範囲限定・既存様式遵守・test-writer のテストを緑にする）／verifier（読んで指摘のみ＝本体・テストコード・文書。成果物に書かない・テストを実行しない）／test-writer（受入条件から実装より先にテストを書く・実装者とは別個体・実装本体は書かない）／test-runner（指定スイートの実行と集計行・失敗行の報告のみ・判断しない）／researcher（裏取り・出典URL・確度必須）／operator（診断のみ・破壊的操作は提案止まり）／adoption-critic（作る・採用する・続けるべきか）。
- **検証職（verifier）**＝作成者とは**別個体**（推奨＝別系統。取れないときは同系統でよく、その旨を成果物と報告に1行明記）が読んで指摘する。起動・裁定はリーダー職（§2）。
- **記録職（vault-scribe）**＝決定済みの内容を外部脳へ書く。内容の新規判断はしない。
- **ナビ職**＝工程ごとのリーダーセッションを起動・管理する最上位の窓口。
- リーダー職は各工程の采配（割り当て・順序・切替・進行）を担う。
- 後戻りコストが高い設計・技術選定は合議＝リーダーが論点定義→各ワーカー・検証職が案・根拠・リスクを出す→リーダーが統合して決定。
- **対象を減らす判定は先に、直列で**＝止められる・減らせる判定（作らない・やめる・止める・BLOCKING）を先に通し、残ったものにだけ次の工程を回す。並行してよいのは互いの対象を減らさない工程だけ。

> 🧊 **ja-doc 職は実測評価後まで凍結**＝職種定義・空席分岐を含めない。
- 委任は職種を名指しで行い、委任文に「向き」を1行書く＝目的・複雑さの上限・不採用の代替案・スコープ外。ワーカーモデルはリーダーが spawn ごとに候補から選ぶ。未採用・空席は §7。

> spawn 時の条文:
> 1. spawn 時に渡す7点（配役の明示指定を含む）
> 2. 配役表の `model` は定義名の候補。リーダーが spawn 前にちょうど1つ選び、ラッパーへ `--model-def <定義名>` で渡す（既定は無い）。判断材料＝[[Preferences/model-catalog]]・[[Preferences/model-definitions-usage]] と【使用率】。具体IDから起動引数を推測しない。再選択点＝①新しい巡 ②上限回復後 ③セッション再開 ④起動失敗時＝使用率を再取得して選び直す。継続は `--resume <session_id>` をリーダーが明示したときだけ・既定は新規起動。
> 3. 配役表は必読にしない。spawn のたびに候補一覧コマンド（`role_candidates.py`・呼び方は同ファイル冒頭の docstring。TSV 7列 `role def route pass ok h5 d7`・`ok=no` は枠上限か resolver 拒否のみ）で候補と枠を照会し、ちょうど1つ選んで条文2へ。`route=subagent` の職種はラッパー起動。
> 4. `execution` が `subagent` 以外の職種は spawn せず、決められた呼び出し口へ `resolve-candidate` の出力をそのまま渡す（exit 非0なら1つも起動しない）。
> 5. **10 分超が見込まれるワーカーは切り離して起動し、完了検知を分ける**＝ラッパーを `nohup … &` で切り離し、完了は Monitor か `until` ループで「出力ファイル非空 ∧ lock 無し」と「失敗（EXIT あり ∧ 出力空）」の両方を見る。前面実行（上限 10 分）に乗せない。再起動前に 0 byte の出力ファイルを消す。
## 2. 品質ゲート
- 成果物は作成者とは別個体による検証を通す（§1）。**起動はリーダー職**＝適用工程の成果物が完成した時点で1回（実装は全実装者の完了後）。巡数＝**単独＝行わない／軽量＝工程ごとに1巡ちょうど・再レビューなし／フル＝工程ごとに1巡以上**。空席時は §7。
- **検証前の形チェック**＝初稿をリーダーが1回通し読み（①方式が目的に対して素直か ②条件・例外の数が目的に釣り合うか ③本人裁定・不採用案と矛盾しないか ④受入条件が観測可能か。①②＝絶対厳守⑥）。通れば検証職へ、違えば作成者へ「向き」を返す。巡ごとの通し読みはしない。
- 標準観点5点＝型設計／静かな失敗／コメント整合／振る舞いカバレッジ／過剰な複雑さ（目的に対して余分な部品・条件・例外・分岐＝絶対厳守⑥）。
- **レビュー先行**＝verifier が読んで指摘し、BLOCKING が1件でもあれば test-runner を回さず即報告。BLOCKING 0 ならリーダーが test-runner に受入条件のスイートを実走させ、集計行・失敗行だけを受け取り、verifier がその結果で受入条件と突合する。
- **テストは実装より先に別個体が書く**＝要件確定後、test-writer が受入条件 1 件ごとにテストを書き（未実装で赤・仕様どおりで緑）、implementer がそれを緑にする。implementer は内部不変条件の追加テストを書いてよいが test-writer のテスト・fixture の置換・弱体化は不可（fixture の修正は test-writer へ差し戻し）。不足している受入条件のテストも test-writer が書く。フル・軽量とも test-writer を立て、単独はリーダーが全部行う。
- リスク部分（永続状態・人間の承認/却下が絡む・複数部品が噛み合う）は詳細設計まで落とす＝状態遷移（失敗・却下・滞留・復活を含む）／source of truth／失敗モード一覧。
- 指摘は全リストで報告。リーダーが1件ずつ**仕分け**（反映／却下＋理由／同じ震源は束ねて1裁定／方針転換）してから作成元へ返す。条件・例外・特例を足して指摘を通す修正は不採用（絶対厳守⑥）。
- **2巡ルール**＝2巡目に BLOCKING が残れば3巡目へ行かず、リーダーが束ね・方針転換を中心に裁定する。重大度が減衰したら打ち切り、残件は明示。本人には巡数・裁定・要判断点だけを渡す。
- **次の巡の深さは前の巡の最高重大度で決める**＝BLOCKING が1件でもあれば修正後に全体を通常どおり検証する。0 なら次の巡は「反映箇所の突合＋担当範囲テストの回帰」に絞った軽い検証1回で締めへ進む。重大度＝BLOCKING 高／MAJOR 中／MINOR 低。
- 締めの2ゲート＝①工程横断の全体構成レビュー ②リーダーによる本番経路 end-to-end スモーク（本番と同じ起動経路で1回以上・初回は本人の目の前で）→通過後に本人の最終レビュー。
- 案件の締めでは、本番ブランチへの取り込みと push の後に作業 worktree とブランチ（backup 含む）を削除する（残すときは理由を案件記録に書く）。
- ワーカーの成果物への修正（指摘の反映含む）はリーダーが直接編集せず作成元ロールへ差し戻す（停止済みでも同じロールを再起動して委任）。
- 長寿命の文書成果物（要件書・設計書級）は、本文（確定事項のみ）と検討経緯（論点・代替案・レビュー録）の2ファイルに分ける（正本＝[[Preferences/coding-doc-style]] §3）。
- **テストの実行範囲**＝ワーカーは委任文で指定された**担当ファイル範囲のテストだけ**を実行する（委任文に**テスト名を明記**）。全テスト一括は**案件の締め（2ゲートの直前）に1回だけ**リーダーの指示で行う（実行は test-runner・固定スイートはリーダー直叩き可）。同じ領域の案件が連続し途中で merge しないなら一括は最後に1回でよい。
- **検証の重さは『その変更が壊しうる対象』で決める**＝委任の前に壊れうるものを1つ挙げる。挙げられない変更（受容済みの値の範囲内の設定変更＝候補の追加・起動時刻・alias 追加など）はテスト・検証職・実装職を付けず、本人指示でリーダーが直接編集→commit→記録1行。構造・契約・読み手コード・新定義を変える変更は通常どおり。
## 3. 作る前の型
- コードを書く必要が出たら、まず既存確認（`~/work` 配下の tools/ と Vault の Preferences・Knowledge）→ 三択（既存拡張／新規／使い捨て）を本人に提案。本人不在時のみ使い捨て暫定・帰還時に必ず報告。

> ⚠️ 置き場は依頼のたびにリーダーが指定する。
> 文書成果物（要件書・設計書級）の既定の置き場＝メイン機ローカル `~/Claude/<案件slug>/docs/`（他機へ配布しない）。案件を独立 private repo で管理するときはその repo の `docs/` でよい（ai-env の repo には入れない）。
## 4. 記録（外部脳）
- フォルダの意味論＝[[Preferences/vault-operation]]。どの機でも6フォルダを持つ（中身は機ごとに独立・Preferences だけメイン機から配布）。
- 書き込みの決定者はリーダー職。執筆は記録職（空席時は §7）。単独モードだけはリーダーが案件の締めに直筆する（[[Preferences/vault-operation]]）。
- 執筆規約＝[[Preferences/vault-operation]]「書き方の鉄則」。Knowledge はカタログ名で作る。
- 読んだノートの綻び（鮮度・リンク切れ・alias 不足）は、直せるなら読み時に直し、直せないなら「Vault記録候補:」で応答に明示する。⚠️ **サブ機で Preferences 発の wiki link の参照先が無いのは常態でリンク切れではない**＝作成・修正・提案・記録候補・綻び報告のいずれもしない（メイン機では直す）。他フォルダ発のリンク切れはどの機でも直す。
- 他の記録規約＝[[Preferences/vault-operation]]
## 5. 公開・git
- push 済みの履歴は書き換えない（追従している他機の pull が ff 不可で止まる）。
- commit は意味の区切り（スライス・工程・締め・export）で切る（1 つに畳まない）。push は repo の可視性で分岐＝private は AI が push・public は本人判断（直前に `gh repo view --json visibility` で実測）。
- git 上の立場は `{{machine_role}}` で決まる＝メイン機は ai-env の2 repo（takumi009-ai-env／-private）へ commit 可。サブ機は2 repo とも pull 専用。他 repo も同じ扱い。pull 専用の repo には push・public 化・Release を提案しない（本人の持ち帰りへ）。
- Preferences の編集・公開スナップショットの生成と commit はメイン機だけ（サブ機は配布物を pull して読むだけ）。
- 公開スナップショットの export（`export-public-vault.sh`）は週次メンテ Phase0 と案件の締め（§2 の 2 ゲート直前）の 2 回だけ行う。
## 6. このコアが実行できないとき（fail-soft）
- コアのルールがこのマシンの能力で物理的に実行できない場合は、作業を止めずに: ①最小の安全側の代替で続行 ②応答に「プロファイル降格候補: <ルールID> / 理由 / 代替として行ったこと」を1行で必ず載せる ③黙って省略しない・コアを書き換えない・既定値を発明しない。
- 申告は出力に出すだけで保管先が無い＝省略しない。
- absolute-rules（層0）は降格対象外＝実行できなければ続行せず本人に上げる。裏取り手段の不足だけは「未裏取りを明示し確度を下げて本人確認へ倒す」で続行してよい（core-conduct §2）。
## 7. 職種が空席のとき
- キーの値が `unknown` なら依存するルールを保留して本人へ上げる。空席は品質ゲートの消滅ではない＝リーダー職が実施するか未実施を成果物に明記する（黙って省略しない）。
- 職種の 4 状態と職種ごとの代替（検証職・記録職・ナビ職・要件/設計/採用判定・列挙外）＝[[Preferences/role-vacancy]]。
