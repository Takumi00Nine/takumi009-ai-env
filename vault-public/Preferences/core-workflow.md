# 仕事の進め方（コア・全マシン共通・最小版）

> 本ノートはコア。**採用の有無も配役も `{{配役表}}` を見る**（表を統合したので `{{採用表}}` という参照名は作らない）。
> コアにモデル名・プラン・アカウント・常駐プロセス名・パスを書かない。
> 出典: 設計書「共通コア分離-設計」§3.2 骨子のうち、§9.0 A-1-2 が採用した7節（§1 は職種名と職務の定義までに限定・§3 は既存確認の条文のみで退避先条文は除外）。凍結側（配役表・validator・版管理）にかかる記述は含めない。

## 1. 職種と役割（定義はここが正本）
- **リーダー職**の職務は4つ＝①最終意思決定 ②記録 ③本人との対話 ④実環境が要る結合検証。
  「作る工程」（要件定義・設計・実装・テスト・調査）は自分でやらず、着手前に担当職種へ委任する。
- **工程7職**＝requirements-analyst（検証可能な受入条件・スコープ外・先行実装調査）／system-designer（代替案比較・構成・テスト戦略。リスク部分は詳細設計まで）／implementer（担当ファイル範囲限定・既存様式遵守・テスト併作）／tester（受入条件と1対1突合・自己申告を信用しない追試）／researcher（裏取り・出典URL・確度必須）／operator（診断のみ・破壊的操作は提案止まり）／adoption-critic（価値の判定＝作るべきか・採用すべきか・続けるべきか）。
- **一次レビュアー職**＝成果物を作った者とは独立した系統から品質を見る。作成者自身が手配し、指摘は全リスト報告・却下の最終採否はリーダー職。
- **記録職（scribe）**＝決定済みの内容を外部脳へ書く。内容の新規判断はしない。
- **ナビ職**＝工程ごとのリーダーセッションを起動・管理する最上位の窓口。

> 🧊 **ja-doc 職は実測評価後まで凍結**（設計書§9.0 B）。採用版コアには職種定義・空席分岐を含めない。
- 委任は職種を名指しで行う。採用の有無も配役も `{{配役表}}`。`agents/*.md` の `model:` は指定しなかった場合の既定値。未採用・空席の扱いは本コア §7 に従う。

> spawn 時の条文（設計書§3.2 §1 復活）:
> 1. 命名は `<配役>-<職種名>`
> 2. spawn 時に渡す7点（配役の明示指定を含む）
> 3. 配役表の `model` の値をそのまま渡す・エイリアスを発明しない
> 4. Bedrock の別名はピン留めが効いている確認が取れなければ渡さず本人へ上げる
> 5. 配役表を読むのはセッション開始時（起動のたびに読み直さない）
> 6. `execution` が `subagent` 以外の職種は spawn せず、決められた呼び出し口から依頼する

## 2. 品質ゲート
- 成果物は、作成者とは独立した系統による一次レビューを、作成者自身が手配して通す（worker-driven）。一次レビューの実体は `{{reviewer}}`。空席時の扱いはコア §7。
- 標準観点4点＝型設計／静かな失敗／コメント整合／振る舞いカバレッジ。
- リスク部分（永続状態・人間の承認/却下が絡む・複数部品が噛み合う）は詳細設計まで落とす＝状態遷移（失敗・却下・滞留・復活を含む）／source of truth／失敗モード一覧。
- 指摘は全リストを省略せず報告し、各件に「修正済み／却下希望＋理由」を付ける。却下の最終採否はリーダー。
- レビュー巡回は重大度が減衰したら打ち切る。打ち切り時に残した指摘は明示する。
- 締めの2ゲート＝①工程横断の全体構成レビュー ②リーダーによる本番経路 end-to-end スモーク（テスト環境と本番環境が違う成果物は、本番と同じ起動経路で最低1回通す。初回は本人が見ている場で）。

## 3. 作る前の型
- コードを書く必要が出たら、まず既存確認（参照先＝`{{inventory_source}}`）→ 三択（既存拡張／新規／使い捨て）を本人に提案。本人不在時のみ使い捨て暫定・帰還時に必ず報告。

> ⚠️ 本節は既存確認の条文**のみ**を採用する（本人裁定・2026-08-30確定）。共通化ファースト・後方互換レイヤ・共有ライブラリ配置・言語ランタイム管理・見た目の作り込み・ja-doc確認の各条文（設計書§3.2 §3の残り）は最小採用から除外し元ノートに残置する。作業スクリプトの退避先・成果物の置き場（`workspace_paths`キー）に関する条文も、最小採用ではこのキーを持たないため除外する。当面は依頼のたびにリーダーが置き場を指定する。

## 4. 記録（外部脳）
- フォルダの意味論＝Fragments 入口／Knowledge 背景／Decisions なぜ／Projects 状態／Preferences 今どう動くか／Personal 個人。このマシンで実在するのは `{{vault_scope}}`。
- 同じルールの正本は1つ。判断は「今どう動くか」と「なぜ」をペアで残す。
- 書き込みの決定者はリーダー職。リーダーは自分で書かない（記録職へ渡す）。Vault への書き込み可否は `{{vault_write}}` に従う。`unavailable` の場合は蓄積する保管先を持たないため、その場の応答に「Vault記録候補:」として明示する。記録職が空席のときはコア §7。
- 執筆規約＝frontmatter 必須／updated 更新／wiki link はフォルダ付きで相互に／aliases 必須／目安8,000字で分割／Knowledge はカタログ名で作る。
- 読んだノートの綻び（鮮度・リンク切れ・alias 不足）は、直せるなら読み時に直し、直せないなら「Vault記録候補:」としてその場の応答に明示する。
- 撤回・白紙化バナーの付いたノートを新しい文脈の材料に使わない。
- project の status は本人の領域＝AI は書き換えない。
- Vault の読み書きは本人へ明示報告する（定常メンテは例外）。

## 5. 公開・git
- リポジトリは必ず private で作り、AI は push まで。public 化は本人が実行する（絶対厳守②）。
- push 済みの履歴は書き換えない。書き換えると、この repo を追従している他のマシンの pull が ff 不可で止まる。
- push 前に未push コミットを1コミットに集約する。
- このマシンの git 上の立場は `{{git_role}}`（repo スコープ付き）。pull 専用の repo には push・public 化・Release を提案しない（本人の持ち帰り事項として上げる）。

## 6. このコアが実行できないとき（fail-soft）
- コアのルールが、このマシンの能力で物理的に実行できない場合は、作業を止めずに次を行う:
  1. その場の代替（最小の安全側）で続行する。
  2. その場の応答に「プロファイル降格候補: <ルールID> / 理由 / 代替として行ったこと」を1行で必ず載せる。
  3. 黙って省略しない・自分でコアを書き換えない・既定値を発明しない。
- 申告は「その場の出力に出す」だけで、蓄積する保管先は持たない。だからこそ、出し忘れれば申告は消える——省略しないことがより重要になる。
- ただし absolute-rules（層0）は降格対象外。層0が実行できない状況に当たったら、続行せず本人に上げる。ただし裏取り手段の不足については、「未裏取りを明示し確度を下げて本人確認へ倒す」で続行してよい（core-conduct §2・`{{web_verification}}`）。

## 7. 職種が空席のとき
- **キーの値が `unknown`（未確認・未記入）のときは、その値に依存するルールを保留して本人へ上げる**のが原則であり、自動的に特定の職種状態へ倒さない（最低契約④⑤）。以下の職種状態の判定も、この原則を前提にする。
- **職種の状態は4つのいずれかになる**（**プロファイルの `role.*` の状態と1:1で対応する**）:
  - `ready`＝採用済み・既定の配役で実行可能性を確認できた（＝空席ではない）。プロファイル側は `configured` に対応。⚠️ **`configured` は `ready` の必要条件であって十分条件ではない**（spawn 失敗時は `vacant_unavailable` へ落ちる＝下記の既存規定）
  - `not_adopted`＝この職種はこのマシンで使わない（採否は各職種の採否を定める既定値に従う。値が無ければ上記のとおり `unknown` として保留し本人に確認する）。プロファイル側は `not_adopted` に対応
  - `vacant_unavailable`＝採用済みだが、既定の配役で実際には動かせない（backend の利用上限・認証失敗・職種定義ファイル不在など）。**ワーカー職の `vacant_unavailable` は、起動を試みて初めて判明する。** spawn が失敗したら `vacant_unavailable` として扱い、本節の代替を発火させる。⚠️ 黙って別の配役で再試行しない。プロファイル側は `unavailable` に対応
  - `vacant_unknown`＝配役が未確定で誰が演じるか決まっていない。プロファイル側は `unknown` に対応（上記の保留原則どおり、依存するルールを保留して本人へ上げる）
- `not_adopted` / `vacant_unavailable` の両方（空席の2状態）で、以下の代替が発火する。**空席は品質ゲートの消滅を意味しない。** ゲート自体は残り、①実施主体がリーダー職へ降りる か ②未実施であることを成果物に明記する、のどちらかになる。黙って省略しない。
- **一次レビュアー職が空席、または `{{reviewer}}` の値が `unknown`**（未確認・未記入）→「一次レビュー未実施（理由）」を成果物と報告に明記して本人判断へ上げる。黙って省略しない。
- **tester が空席** → リーダー職が受入条件と1対1の最小検証を行い、「独立検証なし・リーダー検証のみ」を成果物に明記する。
- **記録職が空席、または `{{vault_write}}` の値が `unknown`／`unavailable`** → 記録内容を「Vault記録候補:」の定型でその場の応答に明示する（リーダーが自分で書かない原則は維持）。
- **ナビ職が空席** → 工程ごとのセッション移動は本人が行う。AI が勝手に代替しない。
- **requirements-analyst / system-designer / adoption-critic が空席** → その工程を飛ばさず、リーダー職が最小限の判定を行い「専任なし」を明記する。
- 上記に列挙が無い職種が空席になったら、代替を発明せず「職種空席: <職種> / 影響 / 代替案」を報告して本人に上げる。
- 空席の判定主体は行によって違う＝リーダー行は機構が起動前に判定し、ワーカー行は採用状況か、起動時の失敗で判明する。空席のときにどう振る舞うかはコア（本節）が決める。この境界を混ぜない。
