# 仕事の進め方（コア・全マシン共通・最小版）

> 本ノートはコア。**採用の有無も配役も `{{配役表}}` を見る**（『採用表』という参照名は作らない）。
> コアにモデル名・プラン・アカウント・常駐プロセス名・パスを書かない。
> 出典＝設計書「共通コア分離-設計」§3.2。圧縮で外した原文＝[[Knowledge/core-rules-compression-archive]]。

## 1. 職種と役割（定義はここが正本）
- **リーダー職**の職務は4つ＝①最終意思決定 ②記録 ③本人との対話 ④実環境が要る結合検証。「作る工程」（要件定義・設計・実装・テスト・調査）は着手前に担当職種へ委任する。⚠️ 例外＝**単独モード＝リーダーが全工程を自分で行う**（職種を1つも立てない）／**軽量モード＝要件定義と設計をリーダーが担当**（実装は委任）。
- **タスク整理が着手の前提**＝新規案件はリーダーがまずタスク一覧を出し、本人の確認を取ってから進める。既存プロジェクトは Tasks 節に従い、**Tasks 節に無い作業は始めない**。本人の発言・ワーカーの発見（差し戻しは除く）・枠の実消費の乖離でタスクが変わったら、止めて Tasks 節を直し確認を取ってから再開する。一覧に載せる3点＝①工程の並びと取捨 ②工程ごとの枠見積りと効く枠 ③残率から出した停止点と再開条件。目安・予備水準＝[[Decisions/2026-09-16-tasks-gate-and-usage-budget]]。要件定義が要るのは①受入条件が自明でない ②「作らない」検討が要る ③後戻りコストが高いとき。モードとは別軸＝[[Decisions/2026-09-16-leader-decides-stages]]。
- **工程7職**＝requirements-analyst（目的・要件・制約の3種を確定まで＝検証可能な受入条件・スコープ外・先行実装調査。**実現手段は条文に書かない**＝[[Decisions/2026-09-17-requirements-scope-purpose-requirements-constraints]]）／system-designer（代替案比較・構成・テスト戦略。リスク部分は詳細設計まで）／implementer（担当ファイル範囲限定・既存様式遵守・テスト併作）／verifier（読んで指摘・受入条件を実行して突合。成果物には書かない）／researcher（裏取り・出典URL・確度必須）／operator（診断のみ・破壊的操作は提案止まり）／adoption-critic（作るべきか・採用すべきか・続けるべきか）。
- **検証職（verifier）**＝作成者とは**別個体**（推奨＝別系統。取れないときは同系統でよく、その旨を成果物と報告に1行明記＝[[Decisions/2026-09-10-verifier-lineage-recommended]]）が読んで指摘し、受入条件を実行して突合する。起動・裁定はリーダー職（§2）。
- **記録職（vault-scribe）**＝決定済みの内容を外部脳へ書く。内容の新規判断はしない。
- **ナビ職**＝工程ごとのリーダーセッションを起動・管理する最上位の窓口。
- リーダー職は各工程の采配（割り当て・順序・切替・進行）を担う。
- 後戻りコストが高い設計・技術選定は合議で決める＝リーダーが論点定義→各ワーカー・検証職が案・根拠・リスクを出す→リーダーが統合して決定する。

> 🧊 **ja-doc 職は実測評価後まで凍結**（設計書§9.0 B）＝職種定義・空席分岐を含めない。
- 委任は職種を名指しで行い、委任文に「向き」を1行書く＝目的・複雑さの上限・不採用の代替案・スコープ外（[[Decisions/2026-09-16-leader-shape-gate-and-triage]]）。採用の有無も配役も `{{配役表}}`。ワーカーモデルはリーダーがspawnごとに候補から選ぶ。未採用・空席は §7。

> spawn 時の条文:
> 1. 配役表に職種行がある職種（候補一覧で `route=subagent` の職種）は `scripts/claude-exec.sh`（別プロセスの headless 起動）で起動する。Agent ツールでは起動できない（フックが拒否する）。名前無し subagent で起動してよいのは配役表に行が無い組み込み `subagent_type` だけ。名前付きは本人指示時の例外＝そのときだけ `<職種名>-<配役>`。理由＝headless の `--agent` 経路では職種定義 frontmatter の `effort:` は実行値にならない（実測＝[[Knowledge/claude-headless-child-facts]]）。effort はラッパーが `--effort` で渡す。
> 2. spawn 時に渡す7点（配役の明示指定を含む）
> 3. 配役表の `model` は定義名の候補。リーダーが spawn 前に候補からちょうど1つ選び、ラッパーへ `--model-def <定義名>` で渡す（既定は無い）。`resolve-candidate` はラッパーが内部で呼ぶ。判断材料＝[[Preferences/model-catalog]] と【使用率】。具体IDから起動引数を推測しない。⚠️ 再選択点＝①新しい巡 ②上限回復後 ③セッション再開 ④起動失敗時＝使用率を再取得して選び直す（[[Decisions/2026-09-14-recast-points-on-resume]]）。継続は `--resume <session_id>` をリーダーが明示したときだけ・既定は新規起動。
> 4. Bedrock系のsubagent候補は `resolve-candidate` が未対応として拒否する。起動対応はローカルLLM段階経路スライスBで扱う。
> 5. 配役表は必読にしない。spawn のたびに候補一覧コマンド（`role_candidates.py`・呼び方は README。TSV 7列 `role def route pass ok h5 d7`・`ok=no` は枠上限か resolver 拒否のみ）で候補と枠を照会し、ちょうど1つ選んで条文3へ。候補一覧で `route=subagent` の職種はラッパー起動（条文1）。
> 6. `execution` が `subagent` 以外の職種は spawn せず、決められた呼び出し口へ `resolve-candidate` の出力をそのまま渡す（exit 非0なら1つも起動しない）。`subagent` の職種はラッパーへ。
> 7. 職種名＝`agents/<職種名>.md` のファイル名＝subagent_type の値＝配役表の `role.<職種名>`（別名で書かない）
> 8. execution が subagent の職種はラッパーで起動する。ラッパーが `resolve-candidate` を呼び、OK 行・`AGENT_MODEL` 行が正しく返らなければ子を起動せず非0で終わる（終了コード表＝要件 §12・README）。effort はラッパーの `--effort` で渡る。定義に effort が無い候補は機の既定 effort で走る。

## 2. 品質ゲート
- 成果物は作成者とは別個体による検証を通す（§1）。**起動はリーダー職**＝適用工程の成果物が完成した時点で1回（実装は全実装者の完了後）。巡数はモードで決まる＝**単独＝行わない／軽量＝工程ごとに1巡ちょうど・再レビューなし／フル＝工程ごとに1巡以上**（指摘があれば作成者が修正して次の巡）。空席時はコア §7。
- **検証前の形チェック**＝初稿をリーダーが1回通し読み（観点4＝①方式が目的に対して素直か ②条件・例外の数が目的の大きさに釣り合うか ③本人裁定・不採用案と矛盾しないか ④受入条件が観測可能か）。通れば検証職へ。違えば検証に出さず作成者へ「向き」を返す。巡ごとの通し読みはしない。
- 標準観点4点＝型設計／静かな失敗／コメント整合／振る舞いカバレッジ。
- **検証職の順序＝レビュー先行**＝読んで指摘し、BLOCKING が1件でもあれば受入条件テストを実走せず即報告（テストは修正後の巡）。実走するときは出力の要約だけ読む（末尾の集計行・失敗時だけ失敗行）＝[[Decisions/2026-09-17-verifier-review-before-tests]]。
- リスク部分（永続状態・人間の承認/却下が絡む・複数部品が噛み合う）は詳細設計まで落とす＝状態遷移（失敗・却下・滞留・復活を含む）／source of truth／失敗モード一覧。
- 指摘は全リストで報告。リーダーが1件ずつ**仕分け**（反映／却下＋理由／同じ震源は束ねて1裁定／方針転換）してから作成元へ返す。条件・例外・特例を足して指摘を通す修正は、指摘が消えても不採用。
- **2巡ルール**＝2巡目に BLOCKING が残れば3巡目へ行かず、リーダーが束ね・方針転換を中心に裁定する。重大度が減衰したら打ち切り、残件は明示。本人には巡数・裁定・要判断点だけを渡す。
- **次の巡の深さは前の巡の最高重大度で決める**＝BLOCKING が1件でもあれば修正後に全体を通常どおり検証する。BLOCKING が0（MAJOR／MINOR のみ）なら次の巡は「反映箇所の突合＋担当範囲テストの回帰」に絞った軽い検証1回で締めへ進む（新規の指摘探しはしない）。重大度＝BLOCKING 高／MAJOR 中／MINOR 低（[[Decisions/2026-09-17-round-depth-by-severity]]）。
- 締めの2ゲート＝①工程横断の全体構成レビュー ②リーダーによる本番経路 end-to-end スモーク（本番と同じ起動経路で1回以上・初回は本人の目の前で）→通過後に本人の最終レビュー。
- 案件の締めでは、本番ブランチへの取り込みと push の後に、作業 worktree とブランチ（backup 含む）を削除する（残すときは理由を案件記録に書く＝[[Decisions/2026-09-14-closing-cleanup-worktree]]）。
- ワーカーの成果物への修正（指摘の反映含む）はリーダーが直接編集せず作成元ロールへ差し戻す（停止済みでも同じロールを再起動して委任）。
- 長寿命の文書成果物（要件書・設計書級）は、本文（確定事項のみ）と検討経緯（論点・代替案・レビュー録）の2ファイルに分ける（正本＝[[Preferences/coding-doc-style]] §3・[[Decisions/2026-08-30-doc-body-archive-split]]）。
- **テストの実行範囲**: ワーカー（implementer・verifier とも）は委任文で指定された**担当ファイル範囲のテストだけ**を実行する。全テスト一括は**案件の締め（2ゲートの直前）に1回だけ**リーダーの指示で行う（実行は検証職でよい）。委任文には**担当範囲のテスト名を明記**する（[[Decisions/2026-09-14-worker-test-scope]]）。同じ領域の案件が連続し途中で merge しないなら、一括は最後に1回でよい（[[Decisions/2026-09-16-batch-full-tests-across-tasks]]）。

## 3. 作る前の型
- コードを書く必要が出たら、まず既存確認（`~/work` 配下の tools/ と Vault の Preferences・Knowledge）→ 三択（既存拡張／新規／使い捨て）を本人に提案。本人不在時のみ使い捨て暫定・帰還時に必ず報告。

> ⚠️ 本節は既存確認の条文**のみ**採用（2026-08-30 本人裁定）。除外した条文は設計書§3.2 §3 に残置（一覧＝[[Knowledge/core-rules-compression-archive]]）。置き場は依頼のたびにリーダーが指定する。

## 4. 記録（外部脳）
- フォルダの意味論＝Fragments 入口／Knowledge 背景／Decisions なぜ／Projects 状態／Preferences 今どう動くか／Personal 個人。どの機でも6フォルダを持つ（中身は機ごとに独立・Preferences だけメイン機から配布）。
- 同じルールの正本は1つ。判断は「今どう動くか」と「なぜ」をペアで残す。
- 書き込みの決定者はリーダー職。単独モードだけはリーダーが案件の締めに自分で書く（Vault 専用マーカーで gate を通す＝[[Decisions/2026-09-07-solo-leader-writes-vault]]）。軽量／フルは記録職へ渡す（空席時は §7）。
- 執筆規約＝frontmatter 必須／updated 更新／wiki link はフォルダ付きで相互に／aliases 必須／目安8,000字で分割／Knowledge はカタログ名で作る。
- 読んだノートの綻び（鮮度・リンク切れ・alias 不足）は、直せるなら読み時に直し、直せないなら「Vault記録候補:」として応答に明示する。⚠️ **サブ機で Preferences 発の wiki link の参照先が無いのは常態でリンク切れではない**（配布は Preferences だけ）＝「この機には無い」扱いで作成・修正・提案・記録候補・綻び報告のいずれもしない。メイン機では直す。他フォルダ発のリンク切れはどの機でも直す（[[Decisions/2026-09-07-out-of-scope-links-not-broken]]）。
- 撤回・白紙化バナーの付いたノートを新しい文脈の材料に使わない。
- project の status は本人の領域＝AI は書き換えない。
- Vault の読み書きは本人へ明示報告する（定常メンテは例外）。

## 5. 公開・git
- リポジトリは必ず private で作り、AI は push まで。public 化は本人が実行する（絶対厳守②）。
- push 済みの履歴は書き換えない（追従している他機の pull が ff 不可で止まる）。
- push 前に未push コミットを1コミットに集約する。
- git 上の立場は `{{machine_role}}` で決まる＝メイン機は ai-env の2 repo（takumi009-ai-env／-private）へ commit 可（push は本人の明示指示時のみ）。サブ機は2 repo とも pull 専用。他 repo は都度本人に確認する。pull 専用の repo には push・public 化・Release を提案しない（本人の持ち帰りへ）。
- Preferences の編集・公開スナップショットの生成と commit はメイン機だけ（サブ機は配布物を pull して読むだけ・`{{machine_role}}` 由来）。

## 6. このコアが実行できないとき（fail-soft）
- コアのルールがこのマシンの能力で物理的に実行できない場合は、作業を止めずに: ①最小の安全側の代替で続行 ②応答に「プロファイル降格候補: <ルールID> / 理由 / 代替として行ったこと」を1行で必ず載せる ③黙って省略しない・コアを書き換えない・既定値を発明しない。
- 申告は出力に出すだけで保管先が無い＝省略しない。
- absolute-rules（層0）は降格対象外＝実行できなければ続行せず本人に上げる。裏取り手段の不足だけは「未裏取りを明示し確度を下げて本人確認へ倒す」で続行してよい（core-conduct §2）。

## 7. 職種が空席のとき
- **キーの値が `unknown` のときは、依存するルールを保留して本人へ上げる**（特定の状態へ倒さない・最低契約④⑤）。
- **職種の状態は4つ**（プロファイルの `role.*` と1:1対応）:
  - `ready`＝採用済みで実行可能性を確認できた。プロファイル側＝`configured`（⚠️ `ready` の必要条件であって十分条件ではない＝spawn 失敗時は `vacant_unavailable`）
  - `not_adopted`＝この職種はこのマシンで使わない（値が無ければ `unknown` として保留）。プロファイル側＝`not_adopted`
  - `vacant_unavailable`＝採用済みだが動かせない（利用上限・認証失敗・定義ファイル不在など）。ワーカー職は spawn の失敗で判明＝この状態として本節の代替を発火（別候補の再試行は1行報告してから）。プロファイル側＝`unavailable`
  - `vacant_unknown`＝配役が未確定。プロファイル側＝`unknown`（保留して本人へ）
- 空席の2状態（`not_adopted`／`vacant_unavailable`）で以下の代替が発火する。**空席は品質ゲートの消滅ではない**＝①リーダー職が実施するか ②未実施を成果物に明記する。黙って省略しない。
- **検証職が空席** → リーダー職が受入条件と1対1の最小検証を行い「独立検証なし・リーダー検証のみ」を成果物と報告に明記する**か**、「検証未実施（理由）」を明記して本人判断へ上げる。
- **記録職が空席** → 記録内容を「Vault記録候補:」の定型で応答に明示する（リーダー直筆はしない。単独モードは記録職を立てない体制であって空席ではない）。
- **ナビ職が空席** → 工程ごとのセッション移動は本人が行う。AI が勝手に代替しない。
- **requirements-analyst / system-designer / adoption-critic が空席** → その工程を飛ばさず、リーダー職が最小限の判定を行い「専任なし」を明記する。
- 列挙に無い職種が空席なら、代替を発明せず「職種空席: <職種> / 影響 / 代替案」で本人に上げる。
- 空席の判定＝リーダー行は機構が起動前に・ワーカー行は採用状況か起動失敗で判明。振る舞いはコア（本節）が決める＝境界を混ぜない。
