# Codex 一次レビュー委任プロトコル（SSOT）

役割分担の全体像は [[Preferences/coding-delegation]]。本ノートはレビュー実行手順の正本。

## 呼び出し方（リーダーが起動する）
**2026-09-06 MCP 経由は廃止＝[[Decisions/2026-09-06-codex-mcp-retire]]。呼び出しは exec ラッパー**（[[Preferences/codex-exec-worker]]）。
- **呼び出すのはリーダー**（適用工程の成果物が完成した時点で1回起動する。実装工程は全実装者の完了を確認してから）。
- 呼び出し口は配役表 `role.verifier` の `execution` に従う（`external-cli`＝`scripts/codex-exec.sh` を背景実行／`subagent`＝`subagent_type: verifier`）。
- `--sandbox` と `--cwd` は**成果物の種別で2経路**＝**文書成果物＝`read-only`**（`--cwd` は成果物の置き場か `$HOME`）／**コード成果物＝`workspace-write`**（`--cwd` は repo の使い捨て worktree へ最小化）。⚠️ **`$HOME` 全体を `--cwd` に渡すときは職種を問わず `read-only`**（権限表の共通則②）。
- プロンプト＝レビュー対象（**ファイルパスで読ませる**。検索させない）＋レビュー観点＋出力形式。**`--out` は worktree の外に置き、最終メッセージの先頭3行を「件数／打ち切り可否／`---`」に固定する。リーダーは先頭3行だけを読む**（リーダーの文脈を守る）。
- **[[Preferences/absolute-rules]] を必ず読ませる**（依頼文に参照を含める。ラッパーが検査し、無ければ起動を拒否する＝呼び出し元を問わず適用）。⚠️ **パス指定で読ませ、本文は貼らない**（`codex exec` は `--cwd` の外の Vault ノートを読める＝実測。ラッパーの文字列検査もパスで満たされる）。
- 裏取りが要るときは `--search` を付ける。
- ⚠️ 起動前に `--out` の親ディレクトリを作り、書けることを確かめる。
- ⚠️ ラッパー自身の stderr を `2> <out>.wrapper.log` へ落とす（事前検査で落ちた理由はここにしか残らない）。
- ⚠️ **`--out` の基底名は試行ごとに変える**（`…-r<N>-a<M>.md`）＝補助ファイルの存在を診断に使うので、使い回すと前の試行の残骸で誤判定する。

## 使用モデルと effort の指標（2026-07-20 追加）
レビューの軽重で GPT-5.6 の3階層＋effort を使い分ける（可用性・実測の正本＝[[Knowledge/gpt-5-6-and-gpt-live]]。exec の `-m`／`-c model_reasoning_effort=` で上書き）:
- **通常の一次レビュー（既定）**: 指定なし＝config の `gpt-5.6-sol`・medium。迷ったらこれ。
- **軽い定型チェック**（形式・命名・小差分・正解が明確な突合）: `-m gpt-5.6-luna`（高速・枠節約）。日常レビューで枠を節約したいときの中間は `-m gpt-5.6-terra`。
- **締めの全体構成レビュー・後戻りコスト高の判断**: 既定 sol ＋ `-c model_reasoning_effort=xhigh`（xhigh は実測で通る）。⚠️**xhigh はこの「品質最優先」場面に限る唯一の例外**（2026-08-07 本人決定＝[[Decisions/2026-08-07-avoid-xhigh-effort]]。それ以外は原則使わない）。
- 実効モデル/effort の確認は `~/.codex/sessions/**/rollout-*.jsonl` の `"model"`/`"effort"`（自己申告は不正確）。`gpt-5.6-sol-ultra`・`gpt-5.6-codex` 等は ChatGPT アカウントでは 400＝使わない。

## 標準レビュー観点セット（2026-07-12 輸入・コード系成果物向け）
プロンプトの「レビュー観点」には、成果物固有の観点に加えて以下の4観点を標準で含める（出典＝Anthropic 公式 pr-review-toolkit の専門エージェント定義から要点を抽出。[[Knowledge/claude-code-official-plugins]]。プラグイン本体は不採用・観点のみ輸入）。文書系成果物では該当分のみ使う。
1. **型設計**: 不正な状態を型で表現不可能にできているか（カプセル化・不変条件の型表現・構築/変更時の強制）。
2. **静かな失敗**: エラーの握りつぶしがないか（空 catch・無言のフォールバック・過度に広い catch・文脈不足のログ・ユーザーへの不明瞭なエラー文言）。
3. **コメント整合**: コメントと実装の一致・前提条件/副作用の記載漏れ・変更で陳腐化するコメント（コメントロット）の検出。
4. **テストの振る舞いカバレッジ**: 行カバレッジでなく振る舞いベースで、主要フロー・エラー処理・境界・負のケースが検証されているか。実装詳細への過剰結合がないか。

## レビュー対象範囲
開発4工程（要件定義/設計/開発/テスト）＝必須。researcher の調査報告・adoption-critic の判定案＝原則乗せる。operator の巡回報告＝対象外。
- **設計工程のレビューでリスク部分は詳細設計まで見る**（2026-07-18）: 永続状態・人間承認/却下・複数部品連携を含む設計は、**状態遷移の網羅（失敗/却下/滞留/復活）・source of truth の明確さ・失敗モードの扱い**を重点観点にする（状態機械の穴・正本のズレを設計段階で潰す＝手戻り前倒し。詳細＝[[Preferences/worker-role-prompts]] system-designer 行）。

## 工程横断・全体構成の最終レビュー（必須・2026-07-18 追加）
per-deliverable の Codex 一次レビュー（コード/行レベル）とは**別レイヤ**として、**開発プロジェクトの締めに「全体構成（アーキテクチャ）レビュー」を必ず行う**（工程横断＝リーダーが呼ぶ）。行単位のレビューは各工程で済むが、**部品同士の噛み合わせ・境界・正本の整合**は別途見ないと抜ける（実証＝2026-07-18 外部脳簡素化で本レビューが構造の粗を7〜8件検出）。
- **タイミング**: 全工程完了＋検証職の検証後、本人最終レビュー/リリース前。**対象＝複数ファイル・新サブシステム・アーキ変更を伴うプロジェクト**（単発の軽微変更は不要）。
- **モデル**: Codex＝既定 sol ＋ **effort `xhigh`**（2026-07-20 更新＝「使用モデルと effort の指標」節。xhigh 実測可を確認済み。旧推奨 high は xhigh 不明時代の値。⚠️xhigh 許容はこの場面のみ＝[[Decisions/2026-08-07-avoid-xhigh-effort]]）。**後戻りコスト高・大規模なものは別モデル（例: Fable 5）でも独立レビューして2者クロス**（2モデルが収束した指摘は信頼度が高い＝実証済み）。
- **観点（構造レベル・行バグは per-deliverable 側の担当で対象外）**: 責任分担/境界の穴・ダブり・取りこぼし（「検出はするが誰も処理しない」等）／ドキュメント正本のズレ・矛盾／状態機械の穴（承認・却下・滞留・整合）／撤去で宙ぶらりんになった機能・死んだ導線／単一障害点・回復不能・静かな全停止／「機械が確定・人間が判断」境界原則の一貫性。
- **処理**: 指摘リスト → **リーダーが再仕分け（「修正で複雑化させない」原則＝消す/減らす/割り切る/直すに分類）** → 本人報告 → 対処 or 受容。対処/受容の判断は Decision か記録に残す（無言放置しない）。

## 締めの必須ゲート②: リーダーの本番経路 end-to-end スモークテスト（正本・必須・2026-07-18 追加）
全体構成レビュー（"読み"の最終ゲート）と並ぶ**リーダー実施の"実走"最終ゲート**（2026-08-08 に [[Preferences/coding-delegation]] から正本を移設）。**成果物がテスト環境と異なる実行環境で動くもの**（スケジューラ＝launchd/cron 実走、別 PATH/権限/ユーザで起動される CLI・自動化、実データ量や外部バイナリ＝claude/python 等の実バージョンに依存するもの）では、**本番と同じ起動経路で最低1回、通しの実走**をリーダーが行い、**ユニット緑でなく「実際に意図通り完走したか」**を確認してから「完了／ロールアウト可」と言う。
- **なぜ必須か**: ユニットテスト・Codex/2モデルレビュー・独立テスターは**すべてテスト環境**での検証で、①OS スケジューラの最小環境（PATH 解決・実行権限・exec）②実バイナリの版（バージョンマネージャ経由の解決差）③外部プロセスの実挙動・実データ量・無人実行の所要時間——**本番固有の要素を一度も踏まない**。**実証＝2026-07-18 外部脳ロールアウト**: 1961ユニットテスト＋2モデルレビュー＋独立テスターが全緑だったのに、本番 launchd スモークで**デプロイ阻害5件**（スクリプト +x 欠落・claude/python の PATH 解決差・max-turns 不足・timeout 不足）が判明。全て「テストが本番経路を踏んでいなかった」ために漏れた＝[[Fragments/2026-07/2026-07-18]] meta教訓。
- **やり方**: 本番の起動器で実走（例: `launchctl kickstart` で対象ジョブを1回起動）→ 完走・意図した副作用（実際の書き込み等）・所要時間・異常なしをログで実測。**初回実走はリーダー＋本人が見ている場で**（変な副作用があれば即 revert できる＝無人の初回稼働を避ける）。破壊的/公開副作用を伴う実走の実行可否は本人ゲート。
- 要件・設計に実行手順（フック等）を書き下ろすときは、本番と同じ実行環境（macOS 標準 `/bin/bash` 3.2 等）で1回走らせてから条文にする（締めゲート②の上流工程への前倒し・2026-09-05 実例＝[[Knowledge/macos-bash32-hook-constraints]]）。
- **対象外**: 純粋なライブラリ/ドキュメント変更等、テスト環境＝本番環境で差が出ないもの（単発の軽微変更と同じ扱い）。

## レビュー巡回の停止基準（2026-07-15 追加）
- モード別の巡数は [[Preferences/core-workflow]] §2 を参照する（「減衰」の定義を二重に持たない）。
レビューは巡ごとに新しい指摘を掘り続け**収束せず漸近する**（実測＝[[Decisions/2026-07-15-implementation-model-trial]]。どのモデルの初稿でも同様）。無限に巡回しないため:
- **打ち切り条件**: 指摘の重大度が「受入条件違反・実運用バグ」から「狭いエッジケース」帯に減衰したら、その巡の対応をもって出荷とする（打ち切り判断はリーダー）。
- 目安: BLOCKING/受入fail が消え、残る MAJOR が実データで踏む見込みの低いケースのみになった巡。
- 打ち切り時に残した指摘は最終報告・記録に明示する（無言の放置にしない）。
- 重大度の減衰だけで打ち切らない。打ち切り前に**観点を変えた1巡**（外部文書・機構の実体・実コードの早期 return との突合）を入れる。同じ観点の連続巡は文書の内部整合に漸近するだけで、外部との不整合は検出されない（2026-09-05 実例＝Codex 8巡目5件→観点転換の9巡目で新規26件）。実例2＝2026-09-06 3モード設計書レビューで、観点を「設計が引用する現物（スクリプト・インストーラ・テスト）との突合」へ変えた1巡が、要件の波及一覧に無い欠陥4件（export-public-vault の worktree 判定・install-main の symlink 配置リスト・update-sub の失敗時 exit 0・同 早期終了）を出した。実例3＝2026-09-06 exec 前提改訂の1〜2巡目（廃止済み MCP で段階1を開始できる記述・Bash 所持の実態の誤認・終了契約の診断先の不在）。
- 指摘を「修正済み」と記録する前に、同じ論点が成果物の別の節にも現れていないか検索して全箇所を直す（差分レビューを1巡で止めると片方だけ直った取り残しが次巡で再検出される＝2026-09-05 実例）。
- 要件書が「減衰」を条文で使うときは、本節の停止基準と同値（BLOCKING と受入条件違反が0件＋残る MAJOR が狭いエッジケースのみ）に書き下ろす。3条件の AND なので、条件ごとに陽性 fixture を置かないと1条件しか検査されない（2026-09-06 実例＝3モード要件 14〜15巡）。
- 同一箇所が4巡連続で型を拡張したら、継ぎ当ても作り直しも止めて「その型を設計工程へ降ろす」（要件は「何が後から再構成できるべきか」だけを定め、表記の文法は設計で決める）ことを検討する。「3巡連続なら型の作り直し」の次段（2026-09-06 実例＝3モード要件の記録の型が12〜15巡で4連続拡張）。
- 「実案件を観察して合否を出す」型の受入条件は、fixture のように入力を固定できないため収束しない。条件を1つ書くたびに「その条件を満たさない実装」が見つかり、レビューが漸近しない（実例＝3モード要件の AC-31 に10〜18巡の指摘が集中し最後まで BLOCKING が消えなかった＝2026-09-06）。要件工程で書き切ろうとせず、観察手順の設計まで降ろすことを早めに検討する。

## 自己レビューバイアスのガードレール
作成者は最終報告に指摘の**全リストを省略せず**載せ、各指摘に「修正済み／却下希望＋理由」を付ける。自明な指摘の修正は作成者が実施してよいが、**却下の最終採否はリーダー**。
却下希望の受け渡し経路＝リーダーは作成者へ指摘リストのファイル（`--out` のパス）を渡し、作成者は読んで修正したうえで、却下したい指摘だけを番号と1行の理由でリーダーへ短く返す（全文は返さない）。リーダーが採否を決め、次の巡の依頼文へ「前巡の却下分とその理由」を載せる。

## 失敗時・スレッド運用
- **stdout の3行が出ているかをまず見る**。出ていない場合は2通り＝**①終了コードが 1／2 で `<out>.wrapper.log` が非空なら事前検査で落ちた**（1＝引数・前提の不備／2＝absolute-rules 不在）／**②`<out>.events.jsonl` か `<out>.stderr.log` があるなら起動後に中断した**（既存プロセスの終了を確かめてからやり直す）。**3行が出ていれば Codex 側の失敗**＝`EXIT:` の値と `<out>.stderr.log` を読む。
- 失敗時: 1回目=情報補完して `--resume` で継続／2回目=再分割。**前景で待たない・止めない・Ctrl-C しない**（**リーダー**は詰まったら中断せず本人へ報告。rollout ログ回収はリーダー＝[[Knowledge/codex-mcp-cancel-desync]]）。
- 継続 vs 新規: 同一成果物の再レビューは継続、別成果物・最新ルール反映時は新規。**スレッドの所有者はリーダー**。
- **Codex のスレッドは日をまたぐと失効しうる**（`Session not found`・2026-09-05 実測・MCP 経由時代の観測。exec の `resume` でも同じ制約が続くかは未検証）。継続往復が前提の差分レビューでは、新スレッドで再開する際に**前巡の指摘全件と各件の反映内容を送信本文へ載せる**（二重指摘・取りこぼし防止）。

## 環境と実行可否
- **検証の起動はリーダー**（`codex exec` はローカル Bash 実行のため MCP 特有の接続設定は不要＝2026-09-06 MCP 廃止＝[[Decisions/2026-09-06-codex-mcp-retire]]）。詳細＝[[Preferences/codex-exec-worker]]。
- **注意**: `~/.claude/agents/*.md` のツール変更は**既存セッションのチームメイトに反映されない**（spawn 時点で固定）。ルール改定直後はフォールバックが要ることがある。
- **フォールバック**: リーダーが Codex を使えない場合（配役表 `role.verifier` が `unavailable`・起動失敗等）は `fallback.verifier` へ落とす（下記「Codex 使用上限時」節）。反映は作成元ロールへ差し戻す（軽微でもリーダーは直接修正しない＝[[Decisions/2026-08-14-deliverable-revision-by-creator]]）。
- **Web 調査は `codex exec --search` で可**（MCP 経由の web_search は2026-09-06実測で不可だったが、同日に呼び出し経路を exec へ一本化＝[[Decisions/2026-09-06-codex-mcp-retire]]。MCP 不可の実測詳細は [[Knowledge/codex-mcp]] 2026-09-06 節に残す）。**依頼文には `--search` を付けるか、Web 裏取りが要るレビューでは依頼側（リーダー・作成者）が一次情報の URL・要旨を添える**（生のネットワーク到達性は本機の `network_access=true` で確認済み）。「Codex はネット不可」を委任回避の理由にしない点は従来どおり（サブ機の誤認事例 2026-09-01。Knowledge はサブへ配布されないため本ノートが正本の届け先）。
- **Codex 使用上限時＝Claude Opus 5 を代替レビュアーに（2026-08-07 本人決定＝[[Decisions/2026-08-07-opus5-fallback-reviewer]]）**: 上限エラーで回復待ちが出荷を止めるなら、リーダーが Opus 5（**`claude-opus-5` 明示・エイリアス「opus」禁止＝4.8 に落ちる**）を単発起動して同一の観点・出力形式でレビューする。effort＝**通常 medium**・締めの全体構成レビューのみ xhigh（本人指定）。独立性低下（Claude 系同士）は許容・後戻りコスト高案件は Codex 回復後に事後クロス可。
- Codex を実装ワーカーとして起動する手順（exec 背景実行・レビュー手順は本ノートのまま）＝[[Preferences/codex-exec-worker]]。

## その他
- Vault 書込は**リーダーの Claude のみ**（Codex・ワーカーは申告→リーダー代筆＝[[Preferences/vault-operation]]）。Codex はクラウド routines 不可。
